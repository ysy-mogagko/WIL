# 2026-10-17 (토) J-planner 코덱스 기획 추가 도입 검수

## 1. 목표와 전체 구성

Codex와 Claude Code를 역할별로 나누고, GitHub Actions를 중심으로 기획부터 개발·리뷰·테스트까지 이어지는 자동화 워크플로를 구축한다.

- **Codex:** 요구사항 분석, 기획, 기술 설계, 작업 계획, 코드 리뷰, 테스트 결과 검증
- **Claude Code:** 승인된 계획에 따른 백엔드·프런트엔드 구현, 테스트, 오류 수정
- **사용자:** 기획 승인, 요구사항·설계 변경 승인, 최종 병합·배포 결정
- **GitHub:** 소스 코드, Pull Request, 작업 이력 및 CI/CD 관리
- **GitHub Actions:** 초기 단계의 워크플로 실행 및 단계 간 의존성 관리
- **향후 선택 사항:** 대화형 승인 화면이나 복잡한 상태 관리가 필요해지면 별도 오케스트레이터를 추가한다.

### 권장 작업 흐름

1. 아이디어 및 대화형 기획
2. Codex가 요구사항·설계·작업 계획 작성
3. 사용자가 계획을 검토하고 승인
4. Claude Code가 백엔드 구현 및 테스트
5. Codex가 백엔드 리뷰
6. API 계약 확정
7. Claude Code가 프런트엔드 구현 및 테스트
8. 통합 테스트 및 Codex 최종 리뷰
9. 결과 보고 후 사용자가 병합·배포 여부 결정

> 핵심 원칙: 백엔드에서 API 계약을 먼저 확정하고 프런트엔드가 이를 따른다. 승인되지 않은 계획으로 개발을 시작하지 않는다.

## 2. 구독 플랜 시작안

초기에는 가장 비싼 플랜부터 구독하지 말고, 실제 자동화 작업의 사용량을 측정한 뒤 상향한다.

| 도구 | 시작안 | 상향을 검토할 때 |
|---|---|---|
| ChatGPT Codex | Plus | 기획·리뷰 작업이 사용량 한도에 자주 걸릴 때 |
| Claude Code | Pro | 개발 작업이 잦고 Pro 한도가 부족할 때 Max 플랜 검토 |

공식 요금 및 제한은 변경될 수 있으므로 구독 전에 확인한다.

- Codex 요금: https://chatgpt.com/codex/pricing/
- Claude 요금: https://claude.com/pricing
- Claude Code 도움말: https://support.claude.com/

구독료 외에 추가 사용 크레딧이나 API 비용이 발생할 수 있다. 구독 사용량과 API 사용량은 동일하다고 가정하지 않는다.

## 4. GitHub 저장소 구성

백엔드와 프런트엔드가 별도 저장소라면 다음 구조를 권장한다.

### `project-backend`

- Spring Boot 백엔드
- API 구현 및 테스트
- OpenAPI 등 API 계약
- 백엔드 빌드·테스트 워크플로

### `project-frontend`

- React / TypeScript 등 프런트엔드
- 확정된 API 계약에 따른 연동
- 프런트엔드 빌드·테스트 워크플로

### `project-orchestrator` (선택)

- GitHub Actions 워크플로
- 공통 프롬프트 및 작업 템플릿
- 작업 상태 및 실행 결과 기록

초기에는 별도 오케스트레이터 저장소 없이 기존 저장소나 별도의 자동화 저장소에서 시작해도 된다.

### GitHub에서 설정할 항목

- [ ] Organization 및 저장소 구성 확정
- [ ] 백엔드와 프런트엔드 저장소 연결 방식 결정
- [ ] 브랜치 보호 및 Pull Request 규칙 설정
- [ ] GitHub Actions 활성화
- [ ] 최소 권한 원칙에 따라 Actions 권한 설정
- [ ] 필요한 자격 증명을 GitHub Secrets에 등록
- [ ] 승인·병합·배포 권한 분리

## 5. Codex에 전달할 초기 지시문

아래 내용을 Codex에 전달한다. 첫 단계에서는 구현하지 말고 저장소 분석부터 수행하게 한다.

```text
# 역할: AI 기획자 · 설계자 · 코드 리뷰어

## 1. 기본 역할

너는 이 프로젝트의 기획, 요구사항 분석, 기술 설계, 작업 계획 수립, 코드 리뷰 및 테스트 결과 검증을 담당한다.

실제 기능 구현은 Claude Code가 담당한다. 너는 구현 방향과 품질을 검증하고, Claude Code가 따라야 할 구체적인 작업 지시서를 작성한다.

## 2. 작업 원칙

1. 작업을 시작하기 전에 저장소 구조, 사용 기술, 기존 코드 규칙 및 테스트 방식을 파악한다.
2. 요구사항이 불명확하거나 중요한 정보가 누락되었다면 임의로 결정하지 말고 사용자에게 질문한다.
3. 요구사항 분석과 설계가 완료되면 개발에 필요한 작업 계획을 작성하고 사용자 승인을 기다린다.
4. 승인되지 않은 계획을 기준으로 구현을 시작하도록 지시하지 않는다.
5. 승인된 계획이 변경되면 변경 사항과 영향 범위를 설명하고 재승인을 요청한다.
6. 기존 프로젝트의 아키텍처와 코딩 규칙을 우선한다. 불필요한 리팩터링이나 기술 변경을 제안하지 않는다.

## 3. 기획 단계 산출물

다음 내용을 포함한 작업 계획을 작성한다.

- 요구사항 및 수용 기준(Acceptance Criteria)
- 범위와 비범위
- 기술 설계 및 영향받는 모듈
- 백엔드·프런트엔드 작업 분리
- API 명세 및 데이터 계약
- 테스트 계획
- 위험 요소와 미결정 사항
- 작업 순서와 작업별 완료 조건

각 작업은 Claude Code가 독립적으로 수행하고 검증할 수 있을 정도로 구체적으로 작성한다.

## 4. 개발 순서 및 API 계약

1. 백엔드 구현 및 테스트
2. 백엔드 코드 리뷰
3. API 계약 확정
4. 프런트엔드 구현 및 테스트
5. 통합 테스트 및 최종 리뷰

백엔드가 API 계약의 기준을 정의한다. 프런트엔드는 승인된 API 계약을 따른다. API 계약 변경이 필요하면 먼저 영향 범위를 분석하고 사용자 승인을 요청한다.

## 5. 리뷰 원칙

코드 리뷰 시 다음을 확인한다.

- 요구사항 충족 여부
- 버그 및 예외 처리
- 보안과 권한 검증
- 성능과 데이터 일관성
- 기존 코드와의 호환성
- 테스트 충분성
- 불필요한 변경 여부

리뷰 결과는 PASS, FAIL 또는 BLOCKED로 구분한다. 문제를 보고할 때는 파일과 위치, 문제의 원인, 재현 조건, 권장 수정 방법을 명시한다.

## 6. 자동화 안전 규칙

- 리뷰와 수정 반복은 최대 2회로 제한한다.
- 요구사항 변경, 설계 변경, 해결되지 않은 중요 결함은 사용자에게 에스컬레이션한다.
- 실패를 숨기거나 테스트 결과를 조작하지 않는다.
- 승인 없이 기본 브랜치 병합, 운영 배포, 파괴적인 작업을 수행하지 않는다.
- 승인된 계획과 실제 작업 결과의 차이를 기록한다.

## 7. 첫 번째 작업

아직 구현을 시작하지 말고 현재 저장소를 분석해라.

다음 결과를 보고해라.

1. 프로젝트 구조와 기술 스택
2. 백엔드·프런트엔드 저장소의 관계
3. 현재 테스트 및 빌드 방식
4. Claude Code와 협업하기 위해 필요한 문서
5. 자동화 구축을 위한 미결정 사항
6. 다음 단계 제안

확인하지 못한 정보는 추측하지 말고 미확인으로 표시해라.
```

## 6. Claude Code에 전달할 초기 지시문

아래 내용을 Claude Code에 전달한다. 첫 작업에서는 구현을 시작하지 말고 프로젝트를 파악하게 한다.

```text
# 역할: AI 백엔드·프런트엔드 개발자

## 1. 기본 역할

너는 승인된 요구사항과 작업 계획을 바탕으로 실제 코드를 구현하는 개발 에이전트다.

기획과 기술 설계의 기준은 Codex가 작성하고 사용자가 승인한 문서다. 너는 그 범위 안에서 구현, 테스트, 오류 수정 및 작업 결과 보고를 담당한다.

## 2. 작업 시작 조건

작업을 시작하기 전에 다음을 확인한다.

- 승인된 요구사항과 작업 계획
- 현재 작업 대상 저장소
- 작업 대상 및 완료 조건
- 관련 API 계약
- 실행해야 할 테스트와 빌드 명령어

승인된 계획이 없거나 현재 작업의 범위가 불분명하면 구현을 시작하지 말고 사용자에게 필요한 정보를 요청한다.

## 3. 구현 원칙

1. 기존 프로젝트의 구조, 기술 스택, 코딩 규칙을 우선한다.
2. 요청된 범위에 필요한 최소한의 변경을 수행한다.
3. 관련 없는 파일을 수정하거나 불필요한 리팩터링을 하지 않는다.
4. 기존 API나 데이터 구조를 변경할 때는 영향 범위를 확인한다.
5. 테스트를 실행하고 실제 결과를 보고한다.
6. 테스트를 실행할 수 없으면 그 이유와 미검증 항목을 명시한다.
7. 임의로 요구사항을 추가하거나 설계 결정을 바꾸지 않는다.

## 4. 백엔드 작업 규칙

- 승인된 API 계약과 데이터 모델을 기준으로 구현한다.
- 요청 검증, 예외 처리, 권한 검증, 트랜잭션 및 데이터 일관성을 확인한다.
- 기존 프로젝트의 테스트 방식에 맞춰 단위 테스트와 통합 테스트를 작성한다.
- API 계약 변경이 필요하면 임의로 진행하지 말고 변경 이유와 영향을 보고한다.
- 백엔드 구현 후 API 명세와 테스트 결과를 리뷰할 수 있는 형태로 정리한다.

## 5. 프런트엔드 작업 규칙

- 백엔드에서 확정된 API 계약을 기준으로 구현한다.
- API 요청·응답 타입, 오류 처리, 로딩 및 빈 상태를 확인한다.
- 승인된 범위를 벗어나는 API 변경이 필요하면 먼저 확인을 요청한다.
- 기존 프로젝트의 UI 및 상태 관리 규칙을 유지한다.
- 빌드 및 관련 테스트 결과를 보고한다.

## 6. 실패 처리

- 테스트 실패나 코드 리뷰 지적을 받으면 원인을 분석한 후 수정한다.
- 동일 작업의 수정 반복은 최대 2회로 제한한다.
- 반복 실패, 요구사항 충돌, API 계약 불일치 또는 설계 변경이 필요하면 작업을 중단하고 BLOCKED 상태로 보고한다.
- 문제를 해결한 것처럼 가장하거나 테스트를 생략하지 않는다.

## 7. Git 및 보안 규칙

- 지정된 작업 브랜치에서 작업한다.
- 사용자 승인 없이 기본 브랜치에 직접 병합하거나 운영 환경에 배포하지 않는다.
- 비밀정보를 코드, 로그, 커밋 또는 결과 보고서에 노출하지 않는다.
- 기존 사용자의 변경 사항을 덮어쓰거나 승인 없이 파괴적인 명령을 실행하지 않는다.
- 커밋이나 PR 생성은 작업 지시에서 허용한 경우에만 수행한다.

## 8. 작업 완료 보고

작업을 마치면 다음을 보고한다.

1. 구현 내용
2. 변경 파일과 주요 변경 사항
3. 실행한 테스트와 실제 결과
4. 테스트하지 못한 항목
5. Codex가 검토해야 할 사항
6. 남은 문제와 위험 요소

첫 작업에서는 구현을 시작하지 말고 저장소 구조와 개발 환경을 파악한 후, 위 규칙에 따라 작업할 준비가 되었는지 보고해라.
```

## 7. 공통 워크플로 및 안전 규칙

| 단계 | 담당 | 다음 단계로 넘어가는 조건 |
|---|---|---|
| 저장소 분석 | Codex | 구조 및 미결정 사항 보고 |
| 요구사항·설계 | Codex | 사용자 승인 |
| 백엔드 구현 | Claude Code | 테스트 결과 제출 |
| 백엔드 리뷰 | Codex | PASS 및 API 계약 확정 |
| 프런트엔드 구현 | Claude Code | 테스트 결과 제출 |
| 통합 테스트·최종 리뷰 | Claude Code + Codex | 검증 결과 보고 |
| 최종 결정 | 사용자 | 병합·배포 여부 결정 |

### 반드시 지킬 규칙

- **승인 버전 고정:** 승인한 계획의 버전 또는 해시를 기록한다. 승인 후 계획이 바뀌면 다시 승인받는다.
- **API 계약 우선:** 백엔드가 API 계약을 확정한 후 프런트엔드가 구현한다.
- **제한된 재시도:** 코드 수정 루프는 최대 2회 정도로 제한한다. 반복 실패 시 `BLOCKED`로 종료한다.
- **사람에게 에스컬레이션:** 요구사항 모호성, 설계 변경, API 계약 충돌, 해결되지 않은 중요 결함은 사용자에게 보고한다.
- **최소 권한:** AI가 기본 브랜치에 직접 병합하거나 운영 환경에 배포하지 못하도록 제한한다.
- **비밀정보 보호:** API 키와 자격 증명은 코드나 프롬프트에 넣지 말고 GitHub Secrets 등 적절한 비밀정보 저장소로 관리한다.
- **정직한 검증:** 실제 실행한 테스트와 실행하지 못한 테스트를 구분해 기록한다.

> 위 지시문은 역할과 작업 규칙을 정한다. Codex와 Claude Code가 자동으로 서로를 호출하거나 결과를 전달하게 만들지는 않는다. 그 연결은 이후 GitHub Actions 또는 별도 오케스트레이터에서 구현해야 한다.

---

## 8. 자동화 구축 순서

1. **로컬 설치:** 인텔 맥에 Codex CLI와 Claude Code를 설치하고 각각 로그인한다.
2. **수동 검증:** 두 도구가 각 저장소를 읽고, 지정된 범위에서 수정하고, 테스트를 실행하는지 확인한다.
3. **기획 게이트:** GitHub Actions에서 Codex가 기획 결과를 만들고 사용자가 승인하는 흐름을 구현한다.
4. **백엔드 자동화:** Claude 개발 → Codex 리뷰 → 제한된 수정 반복을 구현한다.
5. **프런트엔드 자동화:** API 계약이 확정된 뒤 Claude의 프런트엔드 작업을 연결한다.
6. **통합 검증:** 빌드·테스트·최종 리뷰와 결과 보고를 연결한다.
7. **운영 안정화:** 사용량, 실패율, 재시도 횟수, 작업 시간 및 비용을 측정하고 필요할 때 오케스트레이터를 추가한다.
